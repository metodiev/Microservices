### 1. What are microservices?
Microservices are an architectural style where an application is split into multiple small, idenpdent services.

Each service:

- Has a single business responsibility
- Runs independently 
- Can be deployed independently
- Owns its own data
- Communicates via APIs or messaging 

Example:

Instead of one large e-commerce application:

```bash
Monolith:
- User Management
- Payments
- Inventory
- Notifications
```

You split into
```bash
- User service
- Order Service
- Payment Service
- Inventory Service
_ Notification Service
```

Each service can:
- Scale independently (how big it is going to be)
- Use different technologies
- Be deployed separately
- Be maintained by separate teams


### 2. What problems do microservices solve?

Monoliths become difficult when systems grow.

Common monolith problems:

- Slow Deployments
- Large codebases
- Difficult scaling
- Tight coupling (The service is tight to some another functionality, or depends to be called from another monolith logic and depends from it, too tight connections in monolight)
- One bug can crash everything
- Hard for large teams to collaborate (deployment)

Microservices solve these by:
-Isolating functionality
- Enabling team independence
- Improving scalability
- Allowing faster deployments

### Core Characteristics of Microservices

1. Small services

Each service focuses on one business capability.

Example:
- Payment Service 
- Shipping Service
- Authentication Service

NOT:
Gaing "BusinessLogicService"

2. Independent Deployment
Services can be deployed without redeploying the entire system.

Example:
- Deploy Payment Service v2
- Order Service remains unchanged

This is one of the biggest business advantages.

3. Decentralized Data
Each service owns its database

Good:

```bash
Order Service -> Order DB
Payment Service -> Payment DB
```
Bad:
```bash
All Services -> Shared DB
```

Why?

- Prevents tight coupling
- Allows independent evolution
- Improves scalability

4. Loose Coupling
Services should depend minimally on eah other:

Good microservices:
- Communicate through contracts/API's
- Avoid direct DB access
- Hide Implementation details

5. High Cohesion

A service should contain closely related functionality 

Good:
Payment Service:
- charggeCard()
- refund()
- validatePayment()

Bad:
Payment Service
- chargeCard();
- sendEmail();
- generatePDF();


### Monolith VS Microservices

| Feature           | Monolith        | Microservices     |
| ----------------- | --------------- | ----------------- |
| Deployment        | Single unit     | Independent       |
| Scaling           | Whole app       | Per service       |
| Complexity        | Lower initially | Higher            |
| Team autonomy     | Limited         | High              |
| Tech stack        | Usually single  | Polyglot possible |
| Failure isolation | Weak            | Strong            |
| Development speed | Slower at scale | Faster at scale   |

### Advantages of Microservices

Scalability
Scale only needed services.

Example:

- Payment traffic spikes
- Scale Payment Service only

Faster Deployment

Teams deploy independently

Example:
- Notifications updated 10 times/day
- Inventory untouched 

Full Isolation

- Failure in one service doesn't necessarily crash the whole system.

Technology Flexibility

One Service:
- Java + PostgreSQl

Another: 
- Go + Redis

Another: 

Python + ML Moedels

Team Autonomy

Small teams can own services independently

This aligns with
Conway's Kaw

System design mirrors organizational structure

### Disadvantages of Microservices

A strong engineer must understand the tradeoffs.

### Distributed System Complexity
Microservices Introduce:
- Network Failures
- Latency
- Serialization issues
- Partial failures

### Operational Complexity

Need:
- Kubernetes
- Monitoring
- Logging
- Tracing
- CI/CD
- Services discovery

### Data Consistency Challenges

Distributed transactions are hard:

Example:

```bash 
Order created
Payment failed
Inventory already reserved
```

Need patterns like:

- Saga
- Eventual consistency

### More infrastructure

 Microservices require 
 - API gateways
- Message brokers
- Observability platforms
- Service meshes

### When NOT to use Microservices

Do NOT use microservices:

- For small teams
- Small applications
- Early-stage startups
- Simple CRUD systems
- Low-scale products

A modular monolith is often better initially.

### Bounded Context(DDD)
A bounded context defines a clear business boundary.

Example
```bash
- Payment Context
- Order Context
- Shiping Context
```

Each has:

- its own language
- Rules
- Models
- Database

This is the basis for defining service boundaries.

### Service Decomposition
How do you split services?
Common approaches:
By Business Capability

Good:
```bash
Order Service
Payment Service
Inventory Service
```

By Domain (DDD)
Align services with business domains.

By Subdomans:

Example:

```bash
Core
 - payments

 -Notifications

 Generic:
 - Authentication
 ```


 ### SOA vs Microservices

 | SOA                | Microservices          |
| ------------------ | ---------------------- |
| Larger services    | Smaller services       |
| Often ESB-centric  | Smart endpoints        |
| Shared DB common   | Database per service   |
| Heavy governance   | Lightweight governance |
| Enterprise-focused | Cloud-native focused   |

Being ESB-centric means an organization's software infrastructure relies heavily on a centralized "Enterprise Service Bus" (ESB). 
This middleware hub acts as a single intermediary to connect disparate applications, handling all data routing, format translation, and system communication in one place.

### Strangler Pattern
A migration pattern for breaking monoliths.

Process:
1. Keep the monolith running
2. Build new services gradually
3. Route traffic incrementally
4. Slowly replace the monolith.

Use heavily in real enterprise migrations.
